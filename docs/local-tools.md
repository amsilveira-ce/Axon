# Local tools

The Principal Agent gets its capabilities from two places:

- **Remote agents**, discovered at runtime through a [Gateway Agent](architecture.md).
- **Local tools**, which the PA calls *directly* on your own machine.

This page is about local tools. For the command syntax, see
[`axon pa tools`](cli.md#axon-pa-tools).

## What a local tool is

A local tool is an [MCP](https://modelcontextprotocol.io) tool registered
directly with the Principal Agent. When the PA decides a task needs that
tool's capability, it runs the tool itself — no Gateway Agent, no network
discovery, no registration token.

That makes local tools the right choice for capabilities that are:

- **Always available** — they ship with your workspace, so they cannot be
  "offline" the way a remote agent can.
- **Cheap and fast** — no discovery round trip.
- **Local by nature** — reading files on disk, doing math, checking the clock.

| | Local tools | Remote agents |
|---|---|---|
| Registered with | the Principal Agent | a Gateway Agent |
| Discovered | from `local_tools.json` | dynamically, at runtime |
| Needs a token | no | yes |
| Runs | on your machine | wherever the agent is hosted |
| Managed by | `axon pa tools` | `axon token` + `axon add` |

Use a local tool for a self-contained utility. Use a remote agent when the
work belongs to a separate, independently deployed service.

## The default tools

`axon init` registers four local tools, all enabled and ready to use:

| Tool | Capability | What it does |
|---|---|---|
| `calculator` | `calculation` | Evaluates mathematical expressions safely |
| `web_search` | `web_search` | Searches the web via DuckDuckGo (no API key) |
| `file_reader` | `file_reading` | Reads local files — PDF, TXT, CSV, MD |
| `datetime_tool` | `datetime` | Returns the current date/time and resolves date expressions |

All four are served by a single bundled MCP server
(`python -m axon.pa.tools.server`) over the `stdio` transport. You do not need
to install or start anything — they work out of the box.

To see them:

```bash
axon pa tools list
```

## How tools are stored

Registered local tools live in `.axon/pa/local_tools.json`. Each entry has the
shape:

```json
{
  "name": "calculator",
  "capability": "calculation",
  "description": "Evaluates mathematical expressions safely",
  "transport": "stdio",
  "command": ["python", "-m", "axon.pa.tools.server"],
  "enabled": true
}
```

You normally do not edit this file by hand — `axon pa tools` keeps it
consistent for you. Only tools with `"enabled": true` are loaded by the PA.

| Field | Meaning |
|---|---|
| `name` | Unique identifier for the tool |
| `capability` | A tag the PA matches a task against |
| `description` | Plain-language explanation of what the tool does and when to use it |
| `transport` | How Axon talks to the tool: `stdio` or `http` |
| `command` | The command (or HTTP endpoint) that runs the tool |
| `enabled` | Whether the PA may use the tool |

## How the PA picks a tool

The PA does not run tools at random. During intent extraction it works out
which **capabilities** a request needs, then looks for a tool whose
`capability` tag matches.

The `description` is what makes a tool *discoverable*. It is the only thing
the PA reads to decide whether a tool fits a task — which is why
`axon pa tools add` requires it. A vague description leads to the wrong tool
being chosen, or none at all.

> **Write specific descriptions.** *"Searches patient records in the HStory
> EHR"* tells the PA exactly when to reach for the tool. *"Searches records"*
> does not.

## Adding your own tool

Any MCP-compatible tool can be registered. You provide a name, the command
that runs it, a capability tag, and a description:

```bash
axon pa tools add \
  --name sales_report \
  --command "python -m mycompany.tools.sales" \
  --capability sales_data \
  --description "Fetches quarterly sales figures and returns a structured report"
```

### Transports

| Transport | Use it for | The `--command` is... |
|---|---|---|
| `stdio` (default) | A local process — a Python module or an executable | the command that launches it |
| `http` | A tool exposed over HTTP | the endpoint URL |

```bash
# an HTTP tool
axon pa tools add \
  --name crm_lookup \
  --command "http://localhost:9000/mcp" \
  --capability crm \
  --description "Looks up customer records in the internal CRM" \
  --transport http
```

### Validation

Before saving a tool, `axon pa tools add` checks that the command actually
works:

- For `stdio`, it confirms the Python module can be imported, or the
  executable is on your `PATH`.
- For `http`, it confirms the endpoint is reachable.

A tool that fails validation is **not** registered — so you find out at
registration time, not the first time the PA tries to use it.

## Enabling and disabling

You can turn a tool off without losing its configuration:

```bash
axon pa tools disable web_search   # turn it off, keep the entry
axon pa tools enable  web_search   # turn it back on
axon pa tools remove  web_search   # delete it permanently
```

Disabling is handy when you want to temporarily restrict what the PA can do —
for example, cutting off web access for a run that must stay offline.
